# 业务流程交互质量

## 基本原则

业务 UI 不是静态原型。每个可见操作都应该改变状态、改变数据、打开有意义的工作流界面、跳转到相关页面、生成文件，或提供明确确认。

## 筛选规则

- 如果页面按设备、资产、任务、案件或记录筛选，通常也要提供对应上级业务上下文筛选，例如项目、站点、客户、部门、租户、组织。
- 查询必须更新列表或统计结果。
- 重置必须恢复默认条件。
- 级联筛选要保持一致，选择上级后应限制下级选项。

## 状态与 Tab 按钮规则

按钮必须匹配当前状态和当前 tab。

示例：

- 只有未分派或待处理数据才显示分派/指派操作。
- 只有证据/上传 tab 才显示上传证据。
- 只有审核 tab 才显示提交审核。
- 只有确认 tab 才显示确认。
- 只有完成状态才显示归档/关闭操作。
- 打印/导出可以作为全局辅助操作，但不要挤占主要流程按钮位置。

不要在每个 tab 下都堆满所有可能按钮。

## 必须有的反馈

- 查询：刷新可见结果。
- 重置：恢复默认条件。
- 新增/创建：打开弹窗或页面，确认后追加本地/mock 数据。
- 上传/导入：显示已选文件状态，确认后创建可见记录。
- 同步：显示同步中，完成后显示已同步/已更新。
- 启用/停用：原地更新状态。
- 删除：先确认，再移除记录。
- 导出/下载：生成文件或展示具体导出结果。
- 查看/编辑：打开详情面板、抽屉、弹窗或页面，并展示相关内容。

## 文案规则

当系统只是辅助判断、概率识别或决策支持时，使用建议型表达：

- 疑似问题
- 建议复核
- 建议处理
- 建议专家审核
- 草稿报告

除非产品确实具备相应权威，否则避免使用：

- 违法
- 处罚
- 官方结论
- 强制认定

## 验收

- 没有按钮出现在不可能的状态下。
- 没有 tab 展示与自身无关的操作。
- 主流程可以从发现/录入走到分派、处理、审核、确认、归档。
- 按钮反馈可见且有业务意义。
- 如修改了代码，构建通过。
